# Кредитный скоринг по кредитным историям (Альфа-Банк)

Учебный проект по соревнованию Kaggle [alfa-bank-pd-credit-history](https://www.kaggle.com/competitions/alfa-bank-pd-credit-history): по кредитной истории клиента из БКИ предсказать вероятность дефолта (PD).

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/<ВАШ_НИК>/<НАЗВАНИЕ_РЕПОЗИТОРИЯ>/blob/main/notebooks/credit_scoring.ipynb)

## О задаче

* **Задача:** бинарная классификация (`flag = 1` — дефолт). Классы сильно несбалансированы: дефолт у 3,55 % клиентов (примерно 1 к 27).
* **Данные:** одна строка = один кредит клиента, у клиента много строк. Признаки анонимизированы и закодированы небольшими целыми числами.
* **Главная сложность:** таргет задан на уровне клиента, а данные на уровне кредитов, поэтому историю нужно сжать в один вектор признаков на клиента.
* **Метрика:** ROC AUC (дополнительно Gini, KS, PR AUC).

## Данные

| | train | test |
|---|---|---|
| Файлов в исходных данных | 12 | 2 |
| Используется в ноутбуке по умолчанию | 6 (`N_TRAIN_FILES = 6`) | 2 |
| Клиентов | 1,5 млн | 0,5 млн |
| Кредитных записей | около 12,5 млн | около 4,7 млн |

Что показал первичный анализ:

* пропусков нет, дубликатов по паре (`id`, `rn`) нет, номера кредитов `rn` идут без пропусков;
* одна константная колонка: `pre_loans_total_overdue`;
* у клиента в среднем 8 кредитов (медиана 7, максимум 51).

![Распределение таргета](reports/figures/target_distribution.png)

## Что сделано

1. **EDA:** структура данных, таргет, пропуски и дубликаты, распределения признаков, связь с таргетом, корреляции, сравнение train и test (PSI).
2. **Feature engineering:** агрегаты кредитной истории по клиенту (среднее, максимум, минимум, std, доли категорий, статистики платёжной дисциплины, первый и последний кредит), всего 226 признаков.
3. **Валидация:** стратифицированная K-fold кросс-валидация (по умолчанию 5 фолдов), adversarial validation (train против test).
4. **Модели:** логистическая регрессия (бейслайн), LightGBM, CatBoost, бленд по рангам. Подбор гиперпараметров LightGBM в Optuna включён в настройках по умолчанию.
5. **Анализ модели:** ROC и PR кривые, калибровка, децильная таблица (lift), важность признаков, SHAP.

## Результаты

Метрики на out-of-fold предсказаниях (кроме логистической регрессии: она обучалась и оценивалась только на первом фолде):

| Модель | ROC AUC | Gini | KS | PR AUC |
|---|---|---|---|---|
| Logistic Regression (fold 0) | 0,7339 | 0,4677 | 0,3484 | 0,0985 |
| LightGBM | 0,7646 | 0,5292 | 0,3930 | 0,1199 |
| CatBoost | 0,7609 | 0,5218 | 0,3882 | 0,1182 |
| **Бленд (0,7 LightGBM + 0,3 CatBoost)** | **0,7657** | **0,5314** | **0,3957** | **0,1214** |

> Эти значения получены в пробном прогоне: 6 train-файлов, 3 фолда, learning rate LightGBM 0,1, CatBoost до 400 деревьев, без подбора гиперпараметров. Разброс AUC LightGBM по фолдам минимален (0,7645, 0,7649, 0,7645). Параметры по умолчанию в ноутбуке теперь другие (5 фолдов, learning rate 0,04, CatBoost до 3000 деревьев, Optuna включена), поэтому после полного перезапуска цифры в таблице нужно обновить.

Что видно по результатам:

* бустинг заметно лучше логистической регрессии: прирост около 0,03 по ROC AUC;
* бленд даёт небольшой, но стабильный прирост над лучшей одиночной моделью;
* **lift:** в 10 % самых рискованных клиентов доля дефолтов 12,7 % против 3,55 % в среднем (lift 3,57), то есть в эту группу попадает около 36 % всех дефолтов;
* **калибровка** LightGBM близка к идеальной: предсказанные вероятности совпадают с реальной долей дефолтов.

### Какие признаки важны

Сильнее всего работают агрегаты платёжной истории и просрочек: доля кода `0` в платежах (`paym_cnt_v0`), число видов просрочек (`delay_types`), загрузка лимита (`pre_util`) и структура кредитного портфеля (`enc_loans_credit_type`). Чем чаще в истории платежей встречается код `0`, тем ниже риск (по данным это, вероятно, платёж без просрочки). По типу статистики лидирует среднее.

## Ограничение: сдвиг между train и test

Проверки в ноутбуке показали, что train и test заметно различаются:

* **PSI** (первый train-файл против первого test-файла) у признака `enc_loans_credit_type` равен 0,53, у `pre_since_opened` 0,20; значения выше 0,25 считаются сильным сдвигом;
* **adversarial validation:** модель отличает train от test с AUC около 0,93 (при однородных выборках было бы около 0,5);
* в test клиенты в среднем имеют больше кредитов (9,45 против 8,33);
* `enc_loans_credit_type` при этом входит в число самых важных признаков модели.

Поэтому оценка на кросс-валидации может быть выше результата на тестовой выборке. Это стоит учитывать при интерпретации метрик.

## Как запустить

Ноутбук написан для **Google Colab** и берёт данные с Google Drive.

1. Положите папку с данными на Google Drive.
2. Откройте ноутбук в Colab (кнопка сверху).
3. В ячейке раздела 1 проверьте путь `DATA_DIR`.
4. В ячейке «Настройки эксперимента» при необходимости измените:
   * `N_TRAIN_FILES` — сколько из 12 train-файлов использовать (`None` — все; при этом может не хватить памяти в бесплатном Colab);
   * `N_FOLDS`, `LGB_LR`, `CB_ITERS` — число фолдов, learning rate LightGBM и число деревьев CatBoost;
   * `RUN_OPTUNA`, `RUN_CATBOOST`, `RUN_SHAP` — включение и выключение отдельных этапов.
5. Запустите все ячейки (`Runtime → Run all`).

Кэш признаков (папка `cache`) и итоговый `submission.csv` сохраняются в ту же папку с данными. При изменении `N_TRAIN_FILES` или данных удалите папку `cache`, иначе подтянется старый кэш.

Для ориентира по времени: в пробном прогоне один фолд LightGBM (learning rate 0,1) занимал около 4 минут, один фолд CatBoost (400 деревьев) около 4,5 минут. С настройками по умолчанию прогон существенно дольше.

> Запуск локально: замените ячейку с `drive.mount` на обычный путь к данным, удалите строку `!pip install ...` и поставьте зависимости командой `pip install -r requirements.txt`.
